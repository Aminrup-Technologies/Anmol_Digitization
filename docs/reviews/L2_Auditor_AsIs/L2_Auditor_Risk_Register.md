# L2 / Auditor Risk Register (observations only)

**Phase:** RC-014 Phase 1  
**Rule:** evidence-backed observations. No recommended fixes in this file.

| ID | Area | Evidence | Risk |
| --- | --- | --- | --- |
| L2-R01 | Final close / status deadlock | UAT `usp_ProcessApprovalAction` (modify_date 2026-08-01): when all latest days are resolved, role = `Auditor`, and no next approver, header `Status` is set to `'Pending'`. UAT `usp_ForwardApprovalRequest` (2026-09-15) throws 51012 for Auditor. UAT `usp_MarkRequestReadyForPayment` (2026-01-09) requires `Status = 'Completed'` before writing `ReadyForPayment`. | Auditor can finish every day and still cannot persist final close. Ready for Payment UI can appear (`canFinalize`) while the SP returns `Request not completed.` |
| L2-R02 | Repo vs UAT ProcessApprovalAction drift | Repo `Database/Stored Procedures/Approval/usp_ProcessApprovalAction.sql` documents current-approver match, Pending-only header, Completed lock, Manager-cannot-Reject, Auditor-cannot-Return. UAT definition returned by MCP does not contain those guards. | Behavior on UAT is weaker than the repository contract. Role enforcement for day Return/Reject currently lives only in C# (`ProcessDayDetailAction`, `ActionDayRowSilent`). Direct SP callers on UAT can Return as Auditor or Reject as Manager. |
| L2-R03 | Dual day-Reject pipeline | Auditor Reject calls `usp_ProcessSalesApprovalRequestDetail` + `MarkActivityRejectedForDay`. Approve/Return call `usp_ProcessApprovalAction`. The Reject SP (UAT 2026-07-23) has no latest-version predicate, does not sync expenses (C# does), does not recalc header approved totals, and writes history text `'Row Returned'` for a Rejected row. | Rejected days can target a superseded snapshot; expenses/header/history can disagree with Approve path. Duplicate-reject message says “already been returned.” |
| L2-R04 | Latest-version predicate split | C# `LatestDetailWhereForD` and UAT `usp_ProcessApprovalAction` use `MAX(ApprovalRequestDetailId)`. `KeepLatestPerActivity`, `usp_ForwardApprovalRequest`, and `usp_UpdateSalesDailyExpenseStatus` use `MAX(DetailVersion)` then `MAX(ApprovalRequestDetailId)`. `usp_GetApprovalRequestDetails` returns every version. | Grid/modal usually match after the helper. Forward completeness, expense snapshot rewrite, and day approve can theoretically address different rows if version and identity diverge. |
| L2-R05 | Detail SP not latest-only | `usp_GetApprovalRequestDetails` `ORDER BY ApprovalRequestDetailId` with no version filter (UAT 2026-07-30). Binding depends on `KeepLatestPerActivity`. | Any future caller that binds the SP unfiltered will show superseded Pending/Returned snapshots. Expense JSON is duplicated per version. |
| L2-R06 | Stale snapshot updates (expense) | Until 2026-09-15, `usp_UpdateSalesDailyExpenseStatus` could rewrite a non-latest detail (procedure header: “Receipt status updates targeted any snapshot”). Live body now resolves latest version then latest id. Recalc in C# uses MAX(Id) only. Expense SP’s `Snapshot_ExpenseTotal` omits Stationary; C# recalc includes Stationary. | Expense approve/reject and Re-Calculate can write different snapshot totals for Stationary days. Pre-2026-09-15 data may already contain superseded-row edits. |
| L2-R07 | Duplicate / false-success Return | `ProcessDayDetailAction` no-ops when latest status is already Returned. `gvDetails_RowCommand` still shows “Returned Successfully” and row styling. `ActionDayRowSilent` returns `success: false` for the same case. | Not Auditor-primary (Return hidden), but shared code. Postback path misreports success. |
| L2-R08 | Modal refresh after Ready for Payment | `btnMarkReadyForPayment_Click` on success rebinds the detail modal only. It does not call `BindRequestsGrid` or `CloseDetailsAfterSuccessfulForward` (the RC-013 Forward path). Queue SP would drop the row only after header leaves Pending. | Even if L2-R01 is later resolved, Auditor would keep an open modal on a request that has left the queue—same class of UX as RC-013. |
| L2-R09 | ProcessApprovalAction auto-forward vs explicit Forward | UAT `usp_ProcessApprovalAction` still advances `CurrentApproverLoginId` when the last latest day is approved and a next required Pending approver exists. UI also prompts `ShouldConfirmForwardToNextApprover` then `usp_ForwardApprovalRequest`. | L1 last-approve can already move the claim to Auditor before the Forward button. A second Forward then has no next approver (51014) or races. Auditor is not supposed to hit this (`current == max`), but L1→Auditor entry becomes implicit on UAT. |
| L2-R10 | Expense routing / role inconsistency | Comments on `usp_ProcessApprovalAction` say expense role rules belong to `usp_UpdateSalesDailyExpenseStatus`. That SP has no role check (UAT 2026-09-15). `UpdateIndividualExpense` accepts APPROVE/RETURN/REJECT for any session user. Unified cards show Auditor Reject (including on already-Approved expenses) and do not show expense Return. | Auditor can reverse an Approved receipt to Rejected without a day-status change. Managers cannot Reject expenses in UI but the WebMethod would accept REJECT. ClaimStatus vs unused `ApprovalStatus` columns can diverge. |
| L2-R11 | Bulk action edge cases | Bulk Approve skips non-latest IDs and pending/manual receipts. Bulk Reject for Auditor does not require expenses resolved (`TryEvaluateBulkEligibility` Reject → `return true`). `HasPendingReceiptsFromDb` only treats `Pending` and `Returned`; raw `Submitted` is not pending there, but `GetManualExpenseSkipReasonFromDb` does treat `Submitted`. Non-manual (TA/DA) days with `Submitted` expenses can be bulk-approved. | Auditor bulk Reject can reject days with unresolved receipts. Bulk Approve of TA/DA days may proceed while child expenses are still `Submitted`; day APPROVE then force-approves those expenses inside ProcessApprovalAction. |
| L2-R12 | Unified modal remarks | `ActionDayRowSilent` stamps fixed remarks (`Approved/Rejected via Unified Day Modal`) and ignores `txtRowRemark`. | Auditor audit trail for modal day actions does not include typed row remarks. |
| L2-R13 | Queue counters vs queue SP | `UpdateRequestSummaryCounters` counts Returned/Completed/ReadyForPayment on the grid. `usp_GetPendingApprovalsForUser_Filters` only returns `Status = 'Pending'`. | Auditor landing chips for Returned / Completed / Ready For Payment stay 0 even when those states exist in the database. Misleading operational view. |
| L2-R14 | Resubmit always restarts at L1 | `usp_SubmitSalesDailyActivities` RESUBMIT sets `CurrentApproverLoginId = @L1Code`, level 1, and resets **all** approver rows to Pending. | A day returned after L1 Forward (if it occurred) would not return to Auditor. Auditor UI currently blocks day Return, so this is latent unless expenses/whole-claim return or SP-level Return is used. |
| L2-R15 | History insert shape | `usp_MarkRequestReadyForPayment` uses `INSERT INTO ApprovalRequestStatusHistory VALUES (...)` without a column list. Table now has extra nullable columns (`ActionType`, `DetailVersion`, …). | Positional insert depends on column order remaining HistoryId + original six payload columns. Schema drift can break finalize. |
| L2-R16 | Live UI not observed | Integrated browser had no existing UAT session; `https://appsuat.anmolindustries.com/ClaimsApproval_v2.aspx` returned `chrome-error://chromewebdata/`. | Filter/search/pending-queue and modal chrome are documented from markup, not from a live Auditor login. Visual/runtime confirmation is still open. |
| L2-R17 | `usp_ProcessApprovalAction` REJECT unused by UI | SP supports REJECT with latest-version guard and expense/activity sync. Web Forms Auditor Reject uses the older detail SP instead. | Two Reject implementations exist; only the weaker one is on the Auditor click path. |
| L2-R18 | Prior-level Approved days at Auditor | `IsDetailActionableAtCurrentLevel` and `gvDetails_RowDataBound` treat `Approved && DetailApprovedLevel < current` as pending work. Forward completeness uses the same rule. | Expected: Auditor must re-approve L1-approved days. If any path leaves `DetailApprovedLevel` already equal to Auditor level without Auditor action, days would show Done and skip review. |
