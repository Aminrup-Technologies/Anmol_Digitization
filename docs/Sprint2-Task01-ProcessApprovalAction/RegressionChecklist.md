# Regression Checklist — Sprint 2, Task 01 — `usp_ProcessApprovalAction` Hardening

Every test targets `Database/Stored Procedures/Approval/usp_ProcessApprovalAction.sql` directly (call the procedure with the parameters shown) unless noted otherwise. Expected results should be verified both by the procedure's return behaviour (error raised or not) and, for tests that are expected to succeed, by inspecting the affected rows in `SalesApprovalRequestDetail`, `SalesApprovalRequest`, `SalesApprovalRequestApprover`, `SalesDailyActivity`, `SalesDailyExpense`, and `ApprovalRequestStatusHistory`.

All test data should be set up on a non-production database. None of these tests should be run against `AnmolDristiDev` in a way that leaves behind rows that could be mistaken for real claims.

## Required minimum coverage (from the task specification)

| # | Test | Setup | Action | Expected Result |
| --- | --- | --- | --- | --- |
| 1 | **Current approver approves** | A `Pending` request at Level 1, `CurrentApproverLoginId = 'MGR001'`. The latest detail for one activity is `Pending`. | Call with `@ActionBy = 'MGR001'`, `@Action = 'APPROVE'`. | Succeeds. Detail becomes `Approved`, `DetailApprovedBy = 'MGR001'`. No error raised. |
| 2 | **Wrong approver attempts approval** | Same request as #1, still `CurrentApproverLoginId = 'MGR001'`. | Call with `@ActionBy = 'MGR002'` (a different, otherwise valid user — for example a manager on a different claim, or the Level 2 approver on this same claim who has not yet been reached), `@Action = 'APPROVE'`. | Rejected with `'You are not the current approver for this approval request.'`. No row in any table is modified. |
| 3 | **Completed request** | A request with `Status = 'Completed'`. | Call with any valid `@ActionBy`/`@Action`/detail combination, including the login that was last recorded as `CurrentApproverLoginId` before completion. | Rejected with `'This approval request has been completed and is read-only. No further action can be processed.'`. No row in any table is modified, including no new `ApprovalRequestStatusHistory` row. |
| 4 | **Manager rejects day** | A `Pending` request at a Manager level (`ApproverRole` at `CurrentApproverLevel` is not `'Auditor'`), current approver matches `@ActionBy`. | Call with `@Action = 'REJECT'`, `@Remarks` supplied. | Rejected with `'Only the Auditor may reject a day. Managers return a day for correction instead.'`. Detail status unchanged. |
| 5 | **Auditor rejects day** | A `Pending` request at the Auditor level, current approver matches `@ActionBy`. | Call with `@Action = 'REJECT'`, `@Remarks` supplied. | Succeeds. Detail becomes `Rejected`. Activity and its non-approved expenses cascade to `Rejected` per the existing (unmodified) cascade logic. |
| 6 | **Manager returns day** | A `Pending` request at a Manager level, current approver matches `@ActionBy`. | Call with `@Action = 'RETURN'`, `@Remarks` supplied. | Succeeds. Detail becomes `Returned`; header becomes `Returned`; approver row for the current level recorded as `Returned`. |
| 7 | **Auditor returns expense** | *(Out of scope for this procedure — see note below.)* | — | **Not applicable to `usp_ProcessApprovalAction`.** This procedure has no expense-level action; `@Action` only ever represents APPROVE/RETURN/REJECT against a day (detail) row. Expense-level Approve/Return/Reject is owned by `usp_UpdateSalesDailyExpenseStatus`, which was not modified by this task. This test should be tracked against that procedure's own regression suite when it is hardened. Included here only so it is not silently dropped from the requested checklist. |
| 8 | **Audit history generated** | A `Pending` request at Level 1 with a next required approver configured at Level 2. All latest details at Level 1 are `Pending` except the one being actioned, which is the last one outstanding. | Call with `@Action = 'APPROVE'` for the last outstanding detail at Level 1. | Succeeds. A new `ApprovalRequestStatusHistory` row is inserted recording the level completion and handover to Level 2 (unchanged behaviour, verified still present after this task's edits). |
| 9 | **Unauthorized action blocked** | Same as #2, or a request where `CurrentApproverLoginId` is `NULL` (for example, a request in a state where routing has already been cleared). | Call with any `@ActionBy`. | Rejected. When `CurrentApproverLoginId` is `NULL`, rejected with the same current-approver message (the guard treats a `NULL` current approver as "no one may act", not as "anyone may act"). |
| 10 | **Invalid status blocked** | A request with `Status` set to each of: `Draft`, `Submitted`, `Returned`, `ReadyForPayment` (test each individually). | Call with a valid `@ActionBy`/`@Action` combination, using the login last recorded as `CurrentApproverLoginId`. | Rejected with `'This approval request is not currently awaiting approval and cannot be processed.'` in every case. |
