# Gap Analysis — Sprint 2, Task 01 — `usp_ProcessApprovalAction`

Compares the procedure as extracted in the database baseline (`Database/Stored Procedures/Approval/usp_ProcessApprovalAction.sql`, pre-change) against the approved Functional Specification v1.0 and Technical Design Specification v1.0.

| # | Current Behaviour | Required Behaviour | Implementation Required | Risk |
|---|---|---|---|---|
| 1 | `@ActionBy` is accepted as a free-text label and is never compared against `SalesApprovalRequest.CurrentApproverLoginId`. Any authenticated caller who knows a valid detail identifier can process an action, regardless of whose turn it is. | Only the approver currently holding the request may act on it (FS §7.2 R-01; FS §11.1 VA-03; TDS §7.3). | Resolve `CurrentApproverLoginId` from the header and reject the call unless it matches `@ActionBy`. | **Low.** Closes an authorization bypass (hardening review issue G-01 / FS gap G-01). No legitimate caller today depends on acting out of turn; any workflow that does will now fail loudly with a clear message instead of silently succeeding. |
| 2 | No statement in the procedure reads `SalesApprovalRequest.Status`. The procedure will attempt to process an action against a request in any status, including `Draft`, `Submitted`, `Returned`, `ReadyForPayment`, or `Completed`. | An action may be processed only while the header is actively `Pending` (FS §4.3 rule set; FS §11.2 VH-01). | Add a guard requiring `Status = 'Pending'` before the transaction opens. | **Low.** These entry statuses are not valid preconditions for this procedure under the approved workflow today; no legitimate call site passes a non-Pending header. |
| 3 | No guard specific to `Completed`. A `Completed` request is not distinguished from any other status; every write in the procedure remains reachable against it. | `Completed` is fully immutable — no approval action of any kind may be processed against it (FS §9.10 PL-02; FS §4.4 F-11). | Add an explicit, separately-commented guard for `Status = 'Completed'`, ahead of the general status guard, as its own defence-in-depth check. | **Low.** Same basis as #2; called out separately per the task's own numbered requirement and because payment-lock is the single highest-severity finding in the Production Hardening Review (issue 2). |
| 4a | `@CurrentApproverRole` is read but never used to gate any action. `REJECT` is currently permitted for a Manager. | Only the Auditor may reject a day; a Manager must return it for correction instead (FS §8.3–§8.5; FS Rule AU-02/MG-02). | Reject the call when `@NormalizedAction = 'REJECT'` and the resolved role is not `'Auditor'`. | **Low.** Matches the restriction the application layer (`ClaimsApproval_v2.aspx.cs`) already attempts to enforce client-side; this makes it authoritative. |
| 4b | `RETURN` is currently permitted for the Auditor as well as a Manager. | The Auditor may not return a day; only a Manager may (FS Rule AU-02; FS §8.4). | Reject the call when `@NormalizedAction = 'RETURN'` and the resolved role is `'Auditor'`. | **Low.** Same basis as #4a. |
| 4c | The task's role table also lists Approve/Return/Reject **Expense** actions for Manager and Auditor. | — | **Not applicable to this procedure.** `usp_ProcessApprovalAction`'s `@Action` parameter only ever represents a day-level decision (APPROVE/RETURN/REJECT against a detail row); it has no expense-level action. Expense decisions are owned by a separate procedure, `usp_UpdateSalesDailyExpenseStatus`, which is out of scope for this task. | **None.** Recorded as a scope boundary, not a gap, so it is not silently missed. |
| 5 | Detail row records `DetailApprovedBy`/`DetailApprovedOn`/`DetailApprovedLevel`; approver row records `ActionBy`/`ActionDate`/`Remarks`; `ApprovalRequestStatusHistory` is written on level completion, on reaching Completed, and on any other net header-status change. | Preserve all existing audit logging: history, timestamps, remarks, actor (task requirement #5). | None — already satisfied. Verified unchanged after this task's edits. | **None.** |
| 6a | On `APPROVE` completing a level with a next required approver configured, the procedure itself looks up the next approver and writes `CurrentApproverLevel`/`CurrentApproverLoginId` on the header. | `usp_ForwardApprovalRequest` is the sole owner of `CurrentApproverLoginId`/`CurrentApproverLevel` (FS §7.4 R-07; hardening review issue 5 / TDS gap G-04). | Per the refined instruction for this task: **do not disable.** Mark the block with `-- TODO (Sprint 2 - Task 02): Routing responsibility will be migrated to usp_ForwardApprovalRequest.` and leave it fully functional. | **Deferred by design.** Disabling this now, before `usp_ForwardApprovalRequest` is hardened to take over the responsibility, would leave every multi-level claim unable to advance past Level 1 — a functional regression worse than the ownership violation it would fix. Migration is Sprint 2, Task 02. |
| 6b | On `APPROVE` completing a level with no next required approver and the current role is not Auditor, the procedure sets `Status = 'Completed'` and clears both routing columns. | The same single-owner rule applies to `Completed`; per the Functional Specification, `Completed` must never be written by a Manager or Auditor and may only be written by Finance (FS §4.1 Header Status Rules; hardening review issue 8 / TDS gap G-05). | Per the refined instruction: **do not disable.** Mark the block with the same TODO marker and leave it fully functional. | **Deferred by design.** Same basis as #6a — this is currently the *only* path by which a claim reaches `Completed` anywhere in the system (no Finance/payment procedure exists yet, per FS §15.1 / hardening review issue 17). Disabling it now would make every claim permanently unpayable until both `usp_ForwardApprovalRequest` is hardened and a Finance payment procedure is built. |
| 7 | Totals recalculation (§6 of the procedure), mixed-state evaluation (§4), and the CATCH block's message-only error re-raise are all unrelated to the six required rules in this task. | Do not modify unless required by one of the six business rules above (task requirement #7). | None. | **None.** Confirmed no line in these sections was touched. |
