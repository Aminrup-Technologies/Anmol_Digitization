# Phase 3.5 — `usp_HSE_SynchronizeMasters`

**Status:** SQL delivered for independent compile / unit test.  
**Scope:** Master-table upsert only. No employee synchronization. No hierarchy updates. No `ImportBatchMaster.Status` updates. No staging `ImportStatus` finalization (orchestrator owns that).

**Script:** [`Database/Stored Procedures/HRMS/usp_HSE_SynchronizeMasters.sql`](../../Database/Stored%20Procedures/HRMS/usp_HSE_SynchronizeMasters.sql)

---

## 1. Parameters

| Parameter | Type | Direction | Required | Description |
|---|---|---|---|---|
| `@BatchId` | `INT` | IN | Yes | Staging / batch key |
| `@ExecutedBy` | `NVARCHAR(128)` | IN | No | Caller identity (echoed on standalone RS; not persisted on masters) |
| `@MastersInserted` | `INT` | OUT | — | Total rows inserted across all nine master tables |
| `@MastersUpdated` | `INT` | OUT | — | Total rows updated across all nine master tables |

### Example call (standalone)

```sql
DECLARE @MastersInserted INT;
DECLARE @MastersUpdated  INT;

EXEC dbo.usp_HSE_SynchronizeMasters
    @BatchId         = 123,
    @ExecutedBy      = N'test.user',
    @MastersInserted = @MastersInserted OUTPUT,
    @MastersUpdated  = @MastersUpdated OUTPUT;

SELECT @MastersInserted AS MastersInserted, @MastersUpdated AS MastersUpdated;
```

### Orchestrator call (Phase 3.4)

```sql
EXEC dbo.usp_HSE_SynchronizeMasters
    @BatchId         = @BatchId,
    @ExecutedBy      = @ExecutedBy,
    @MastersInserted = @StepMastersInserted OUTPUT,
    @MastersUpdated  = @StepMastersUpdated OUTPUT;
```

Compatible with `usp_RunHRMSSynchronization` OUTPUT contract from doc 17.

## 2. Transaction scope

| Scenario | Behaviour |
|---|---|
| Standalone (`@@TRANCOUNT = 0` at entry) | Procedure begins its own transaction, commits on success, rolls back on error |
| Nested under orchestrator (`@@TRANCOUNT > 0`) | Joins the ambient transaction; does **not** commit/rollback the outer work |
| Hard SQL error (nested) | Re-raises; orchestrator `CATCH` performs full `ROLLBACK` |
| Hard SQL error (standalone) | Local `ROLLBACK` + re-raise |

`SET XACT_ABORT ON` is set for consistent abort behaviour.

## 3. Synchronization order

Fixed order (must not be rearranged without impact analysis):

| Step | Target table | Staging business key | Staging description |
|---|---|---|---|
| 1 | `MST_Region` | `Region_ID` | `Region_Description` |
| 2 | `MST_Division` | `Division_ID` | `Division_Description` |
| 3 | `MST_Category` | `Category_ID` | `Category_Description` |
| 4 | `MST_Branch` | `Branch_ID` (INT) | `Branch_Description` |
| 5 | `MST_Plant` | `PlantID_ID` | `PlantID_Description` |
| 6 | `MST_Department` | `Department_ID` | `Department_Description` |
| 7 | `MST_SubDepartment` | `SubDepartment_ID` | `SubDepartment_Description` |
| 8 | `MST_Grade` | `Grade_ID` | `Grade_Description` |
| 9 | `MST_Designation` | `Designation_ID` (business code) | `Designation_Description` |

**Out of scope for this procedure:** `MST_Company`, `MST_UserMaster`, reporting hierarchy columns.

**Source filter (every step):**

```sql
FROM dbo.Staging_EmployeeData
WHERE BatchId = @BatchId
```

Never references `KKM_SO_TADA_Export_14Nov25$`.

## 4. Update rules

For each master table:

1. Build a distinct set of non-blank staging business keys for `@BatchId`.
2. Aggregate description with `MAX(NULLIF(LTRIM(RTRIM(Description)), ''))` per key (stable pick when a batch has conflicting descriptions).
3. `UPDATE` the master row matched on business key when:
   - staging description is non-empty, **and**
   - current master description differs (`ISNULL(master.Descr,'') <> staging.Descr`).
4. Descriptions are written with `LEFT(..., 50)` to match known `varchar(50)` master description columns.
5. Business-key match styles align with `usp_HSE_ValidateBatch`:
   - Direct equality: Region, Department, Grade, Designation
   - `TRY_CONVERT(INT, …)`: Branch
   - `CAST(master.Key AS NVARCHAR(50)) = staging.Code`: Division, Category, Plant, SubDepartment

No deletes. No updates to `Id` identity values.

---

## 5. Insert rules

For each master table:

1. Use the same distinct staging key/description set as the update step.
2. `INSERT` when:
   - staging description is non-empty, **and**
   - no master row exists for that business key.
3. Insert columns are only the business key + description (identity `Id` is generated by the table).
4. Codes with blank/NULL description are **not** inserted (matches ValidateBatch: unresolved code without description cannot be created).
5. Blank staging codes are ignored (optional org fields).

### Designation mapping preserved

```text
Staging_EmployeeData.Designation_ID   (HRMS business code)
        ↓ match
MST_Designation.Designation_ID        (varchar code)
        ↓ later employee sync uses PK
MST_Designation.Id
        ↓
MST_UserMaster.Designation_ID         (int FK to Id)
```

This procedure only maintains `MST_Designation` by **business code**. It does not write `MST_UserMaster`.

### SubDepartment note

`HrmsDataImport.ExpectedDbColumns` currently omits `SubDepartment_Description`, while the ZingHR CSV and `MST_SubDepartment` both use that name. This procedure expects `Staging_EmployeeData.SubDepartment_Description` to exist. If the column is present but unmapped (NULL), SubDepartment insert/update counts remain `0` — consistent with ValidateBatch treating unresolved SubDepartment without description as non-creatable.

## 6. Result set contract

### OUTPUT parameters (always; orchestrator contract)

| Output | Meaning |
|---|---|
| `@MastersInserted` | Sum of insert rowcounts for steps 1–9 |
| `@MastersUpdated` | Sum of update rowcounts for steps 1–9 |

### Client result set (standalone only)

Returned **only** when the procedure started its own transaction (`@StartedTran = 1`).  
Suppressed when nested under `usp_RunHRMSSynchronization` so BatchManager `SqlDataAdapter.Fill` still binds the orchestrator summary as the first (and only) result set.

| Column | Type (logical) | Meaning |
|---|---|---|
| `BatchId` | int | Echo of input |
| `MasterTable` | nvarchar | One of the nine `MST_*` names |
| `InsertedCount` | int | Rows inserted for that table |
| `UpdatedCount` | int | Rows updated for that table |
| `ExecutedBy` | nvarchar | Echo of `@ExecutedBy` |

Nine rows, ordered in synchronization order.

### What this procedure does **not** return / mutate

| Item | Behaviour |
|---|---|
| `ImportBatchMaster.Status` | Unchanged (orchestrator) |
| `Staging_EmployeeData.ImportStatus` | Unchanged (orchestrator finalizes Pending → Processed) |
| Employee / hierarchy counts | N/A |

## 7. Error handling

| Condition | Result |
|---|---|
| `@BatchId` null / ≤ 0 | `RAISERROR`, return (no tran) |
| Batch missing in `ImportBatchMaster` | `RAISERROR`, return |
| No staging rows for batch | `RAISERROR`, return |
| Runtime DML / conversion failure | Rollback local tran if owned; re-raise for orchestrator |
| Soft “code without description” | Skipped (not an error); ValidateBatch should have blocked those rows earlier |

## 8. Test cases

| ID | Scenario | Setup | Expected |
|---|---|---|---|
| T01 | Guard: bad BatchId | `@BatchId = 0` | Error; OUTPUTs remain 0 |
| T02 | Guard: unknown batch | Non-existent BatchId | Error |
| T03 | Guard: empty staging | Batch exists, 0 staging rows | Error |
| T04 | Insert new Region | New `Region_ID` + description | `@MastersInserted` ≥ 1; `MST_Region` row created |

| T07 | Skip code without description | New `Grade_ID`, blank description | Not inserted; no hard error |

| T09 | Designation by business code | New `Designation_ID` + description | Row keyed by `Designation_ID`, not by `Id` |
| T10 | Full order run | Batch with all nine master types new | Standalone RS has 9 rows; non-zero inserts where descriptions present |
| T11 | Nested under orchestrator | `BEGIN TRAN; EXEC …; ROLLBACK` | No client RS from child; OUTPUTs populated; rollback removes master DML |
| T12 | No employee side effects | Trace / before-after `MST_UserMaster` | Zero employee inserts/updates |
| T13 | No hierarchy side effects | Trace reporting manager columns | Unchanged |
| T14 | Idempotent re-run | Execute twice on same batch | Second run: inserts 0; updates 0 if descriptions unchanged |
| T15 | Orchestrator rollup | Call via `usp_RunHRMSSynchronization` with `MASTER` module | Summary `MastersInserted` / `MastersUpdated` match child OUTPUTs |

## 9. Assumptions

1. Validated SSMS master upsert intent is preserved as: **match business key → update description if changed → insert missing when description present**, with source swapped to `Staging_EmployeeData WHERE BatchId = @BatchId`.
2. Master tables expose `{Key}` + `{Description}` (Plant uses `PlantID_*` naming).
3. `Staging_EmployeeData` includes the ID/Description columns listed in §3, including `SubDepartment_Description`.
4. `MST_Company` remains out of scope for this phase (still validated by `usp_HSE_ValidateBatch`).
5. UI/ASPX/C# are unchanged; BatchManager continues to call the orchestrator only.
